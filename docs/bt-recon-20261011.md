### 1.5 对比 Linux 是怎么匹配的

```
$ curl -sS .../torvalds/linux/master/drivers/bluetooth/btusb.c | grep -n 0e8d
97:	{ USB_DEVICE(0x0e8d, 0x763f) },
648:	{ USB_VENDOR_AND_INTERFACE_INFO(0x0e8d, 0xe0, 0x01, 0x01), ... }   <- 关键
690:	{ USB_DEVICE(0x0e8d, 0x0608), .driver_info = BTUSB_MEDIATEK | ... }
```

Linux 的通用规则是 **`USB_VENDOR_AND_INTERFACE_INFO`**：vendor `0x0e8d` + **接口**类 `0xE0/1/1`。
也就是说 Linux 明确知道这类设备要在**接口**层级匹配 —— 与我们的描述符形态一致。

## 2. 判断

### 2.1 第一个卡点：**没有任何 personality 能匹配我们的设备**

`0e8d:0616` 逐条比对 41 个 personality：

| 候选 | 要求 | 我们的设备 | 结果 |
| --- | --- | --- | --- |
| `SimpleMtkBtFw_MT7921_0e8d_0608` | idProduct = `0x0608` | `0x0616` | ✗ |
| `SimpleMtkBtFw_MediaTek_Generic` | **设备级** `bDeviceClass=0xE0, bDeviceSubClass=1, bDeviceProtocol=1` | 设备级 `0xEF/2/1` | ✗ |
| 其余 39 条 | OEM VID/PID | 不匹配 | ✗ |

⇒ **kext 根本不会 attach 到设备上**，`BtMtk::setup()` 一行都不会跑，固件也不会下载。

⚠️ **交接文档 §6 的"我们的设备 VID 与类都符合"是错的。** 那句话的依据是 `iorg` 里读到的
**接口类** `0xE0`（在 `BT_ACL_If` 上），而这个 personality 匹配的是 **`IOUSBHostDevice` 的设备类**。
两者在同一台设备上并不是同一个值。**这是本次调研最重要的一条更正。**

### 2.2 假设它 attach 上了，运行时流程大概率能接受我们的芯片

`BtMtk.cpp:74-136` 的判定链：

```
readDeviceId(0x80000008, &devId)        // ROM 自报
if (!devId || devId != 0x7663)          // 0x7663 = MT7663，不是我们
    readDeviceId(MTK_BT_READ_DEV_ID, &devId)   // MTK_BT_READ_DEV_ID = 0x70010200
...
switch (devId) {
case 0x7922:   // MT7922 —— 我们
case 0x7961:   // MT7921
    buildFirmwareName(...) -> BT_RAM_CODE_MT7922_1_1_hdr.bin  （已内嵌在 kext 里）
    setupFirmware79xx(...)
```

Linux 侧同一套寄存器（`btmtk.c:1324-1331`：先 `0x80000008`，再 `0x70010200`），
且 `btmtk.c:872/972` 对 `dev_id == 0x7922` 有专门的 subsys_reset 处理 ——
SimpleMtkBtFw 的 `BtMtk.cpp:474/531` 逻辑与之一致。

⇒ RZ616 = MT7922，内部 ID 应读回 `0x7922`，落在已支持分支内。
**（这一条是推断，未实测 —— 因为现在没有驱动绑定，读不到那个寄存器。）**

### 2.3 绑定后它是怎么把蓝牙交给 macOS 的（架构上没问题）

`SimpleMtkBtFw.cpp:36-86`：

```c
m_pDevice = OSDynamicCast(IOUSBHostDevice, provider);   // 匹配的是"设备"
...
m_pBTMtk->setup();                                      // 走 USB 控制传输下固件
publishReg(true, fwName);                               // 打 FirmwareLoaded / fw_name
cleanUp();                                              // m_pDevice->close(this)
```

`publishReg()` 里还有一句（`version_major >= 21`）：

```c
m_pDevice->setName("Bluetooth USB Host Controller");
```

⇒ 下载完固件后**主动 close 并把设备改名**，让苹果自带的蓝牙 USB 传输驱动接走。
这与 README 的"不是独立蓝牙协议栈，固件初始化完成后蓝牙功能由 macOS 接管"一致。
**这是正确的架构选择**：AirDrop/接力需要的是苹果那套协议栈，不需要自己写。

`USBDeviceController.cpp:84-118` 的 `findInterface()` 会遍历子接口、
要求"HCI 端点齐（interrupt-in + bulk-in + bulk-out）"、并优先选 `bInterfaceClass==0xE0 && sub==1 && proto==1` 的那个 ⇒
我们三个 0xE0 接口里只有 `BT_ACL_If`（3 端点）会被选中。

### 2.4 两个额外发现

**（a）本机无法从源码构建。**

```
$ xcode-select -p
/Library/Developer/CommandLineTools
$ xcodebuild -version
xcode-select: error: tool 'xcodebuild' requires Xcode, but active developer directory
                   '/Library/Developer/CommandLineTools' is a command line tools instance
```

这是 Xcode 工程，没有完整 Xcode 就 `xcodebuild` 不了。但上游有**官方发布包**（tag 1.0.0，
`SimpleMtkBtFw-1.0.0-RELEASE.zip`），里面就是两个现成 kext ⇒ **可以只改 Info.plist，不需要编译**。
（与本仓 `AirportMtk.kext` 同样是无签名注入，本机 `amfi_get_out_of_my_way=0x1 amfi=0x80` 已放宽，路径已被验证可行。）

**（b）补丁 kext 会全局 hook 一个 USB 核心函数 —— 这是真正需要单独评估的风险项。**

`SimpleMtkBtPatcher.cpp:126-140`，在 Monterey+ 上：

```c
KernelPatcher::RouteRequest hostDeviceRequest {
    "__ZN15IOUSBHostDevice13deviceRequestEP9IOServiceRN11StandardUSB13DeviceRequestEPvP18IOMemoryDescriptorRjP19IOUSBHostCompletionj",
    newHostDeviceRequest, oldHostDeviceRequest };
patcher.routeMultiple(index, &hostDeviceRequest, 1, address, size);
```

即用 Lilu 路由 **`IOUSBHostDevice::deviceRequest`** —— 本机**所有** USB 设备类请求都会经过这个钩子
（本机 USB 设备很多：鼠标、键盘、麦克风、手机、TESLADRIVE 等）。
钩子本身只在看到 HCI opcode `0x200B`(LE Set Scan Param) / `0x0C03`(Reset) 时才动手，
其余原样透传；但它会对带 descriptor 的请求做 `prepare/readBytes/complete`。

**依赖关系**：`SimpleMtkBtFw.kext` 的 `OSBundleLibraries` 只有
`IOUSBHostFamily / kpi.iokit / kpi.libkern / kpi.mach` —— **不依赖 Lilu**；
只有 `SimpleMtkBtPatcher.kext` 依赖 `as.vit9696.Lilu 1.2.0`。

⇒ **可以分两步：先只上 SimpleMtkBtFw.kext（零 Lilu 补丁、零 USB 核心 hook），
确认固件能下载、macOS 能接手；确认之后再单独决定要不要上 patcher。**

## 3. 哪些是实测的、哪些是推断的

**实测（命令输出在本文 §1）**

- 我们的设备级描述符是 `0xEF/2/1`，接口级是 `0xE0/1/1`（ioreg）
- 蓝牙接口上没有任何厂商驱动绑定（ioreg）
- `system_profiler` 报的 `BCM_4350C2` 来自 `IOBluetoothFamily` 且 provider 是 `IOResources` ⇒ 兜底占位
- 上游 41 个 personality 的完整匹配条件，以及 `0e8d` 名下只有 `0x0608` 与"设备类 0xE0"两条
- 本机 `xcodebuild` 不可用（只有 CommandLineTools）；官方有 1.0.0 发布包
- 上游运行时只接受 devId `0x7922`/`0x7961`；固件 `BT_RAM_CODE_MT7922_1_1_hdr.bin` 已内嵌
- patcher 路由的是 `IOUSBHostDevice::deviceRequest`，且只有它依赖 Lilu
- Linux `btusb.c` 对 MediaTek 用的是 vendor + **接口类** 匹配

**推断（未实测，已标注理由）**

- RZ616 的内部 devId 读回 `0x7922`：依据是 Linux `btmtk.c` 同一组寄存器与 `dev_id == 0x7922`
  的专门分支，以及本机是 MT7922 硅片。**没有驱动绑定就读不到那个寄存器，只能等装上后实测。**
- 加上 `0e8d:0616` 的 VID/PID personality 后能否真的 attach 并 `open()` 成功：
  依据是 IntelBluetoothFirmware（同源代码血缘，`zxystd`）在同类 IAD 复合设备上可行，
  **但本机未验证**。这是下一步要实测的第一件事。

**本轮未做的事**：没有写入 ESP、没有改任何系统文件、没有安装任何 kext。
