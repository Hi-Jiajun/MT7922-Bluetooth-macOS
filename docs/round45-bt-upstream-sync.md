## 1. 驱动：**我们已是最新**（实测）

上游 `laobamac/SimpleMtkBtFw` 的 releases 页只有一个版本：**1.0.0** ——
正是本机 `tools/bt-payload/` 里那份（`CFBundleVersion 1.0.0`）。

唯一差别：上游 master 的 `FwBinary.cpp` 里固件比 1.0.0 发布包**略新**
（`20251118163447` vs `20251118163139`，**同一天**）。所以"换驱动"没有对象可换。

## 3. 官方文档：**没有公开的**（结论同 Wi-Fi）

检索 MT7922 蓝牙固件接口/编程参考，结果全是论坛帖，没有 PRM/数据手册。
但公开渠道有两条**有价值**的信息：

1. **MediaTek 自家 Windows 驱动覆盖本设备**（Dell/HP 分发的
   `MediaTek MT7920/MT7921/MT7922/MT7925 Bluetooth UWD`），
   本机 Windows 分区里 `mtkbtfilter` 就是它 —— 与 Wi-Fi 侧同理，
   这是厂商一方的可用参照。
2. **Linux 侧存在"驱动版本敏感"的实测案例**（Ubuntu 2026-08 报告）：
   同硬件、**同固件文件**，内核从 `7.0.0-29` 升到 `-30` 后蓝牙起不来
   （`Failed to send wmt patch dwnld (-110)` / `Failed to set up firmware`），
   **回退内核立即恢复** ⇒ 这是**驱动回归**而非固件问题。

第 2 条对本项目有直接含义：**失败可能出在驱动侧而不是固件侧**，
而上游那个 `SimpleMtkBtPatcher.kext` 正是为这类"主机侧兼容"问题存在的。

## 4. 打通了"无 Xcode 重建"这条链（本轮最大产出）

上游构建写死 `xcodebuild`，本机没有。要换固件就必须绕开它 —— **已经绕开了**。

产物与上游发布版逐项对比：

| | 段数 | nm 符号数 | 未定义符号 | `_kmod_info` |
| --- | --- | --- | --- | --- |
| 我们重建 | 9 | 457 | 326 | 有（`0x144f40`） |
| 上游发布 | 9 | 445 | 329 | 有（`0x142ec0`） |

### 打通时踩到的两个坑（都是实测，且第二个是"假通过"）

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| `zutil.c` 必须按 **C++** 编译 | 按 C 编译报 `expected identifier or '('` —— 它体内写着 `extern "C" {`，而它后面的 `_start`/`_stop` 又在 `extern "C"` **之外**，名字被修饰成 `__Z5_stopP9kmod_infoPv` | 全按 C++ 编译 |
| **缺 `_kmod_info` 符号** | 首次链接"成功"，**段列表与上游发布版逐项相同**，但 `nm` 里只有两个 `_start/_stop`，没有 `_kmod_info`；内核会以 *kexts must have a _kmod_info symbol* 拒绝 | 手写 `kmod-info.cpp` 定义它（本仓 Wi-Fi 驱动 `kmod-info.c` 是同样做法） |

**第二个坑的教训值得记下**：我先用 `strings \| grep kmod_info` 验证，判为"通过"，
后来发现段名不是独立字符串、这个检查**根本验不出来**，改用 `nm` 才看见真缺失。

## 6. 我的建议：**先测基线，不要抢先换固件**

理由是证据，不是保守：

| 理由 | 说明 |
| --- | --- |
| **蓝牙从未运行过** | kext 刚注入、还没重启。我们还不知道当前固件能不能下载成功、`regRead` 返回什么 |
| **本项目已有一次反例** | Wi-Fi 侧把固件换成"最新"（2026-07-24）**并没有修好任何问题**。所以"最新固件"在本项目里不是已验证的修法 |
| **重启是最稀缺的资源** | 基线先跑，才能知道到底该换固件、还是上 patcher、还是别的问题 |
| **换固件现在是"一条命令"** | 重建链已通，`SRC_DIR=./src-newfw bash build-bt2.sh` 即可，随时可做 |

**推荐的判读顺序**（重启后）：

1. 若日志出现 `reg=0x70010200 value=0x7922` 且 `MediaTek device setup complete`
   ⇒ 基线就是好的，**不需要换固件**；
2. 若 `Unsupported MediaTek hardware variant` ⇒ 是 devId 判定问题，换固件无用，要看 patcher；
3. 若固件下载失败/超时 ⇒ **这才轮到换新固件**（`out-new/`），
   因为它与"固件内容"直接相关；
4. 若固件下载成功但蓝牙功能异常 ⇒ 更可能是**驱动侧**（参照 §3 第 2 条的 Linux 案例），
   下一步是上 `SimpleMtkBtPatcher.kext`，而不是换固件。
